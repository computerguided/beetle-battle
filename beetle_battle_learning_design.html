The original Beetle Battle shipped with a hand-tuned evaluation function: a human decided that corners were worth three points, edges two, and so on.1 This document describes the learning edition, in which the computer is given none of that knowledge. It plays thousands of games against itself, observes which positions tend to lead to victory, and discovers its own evaluation function. The method is afterstate temporal-difference learning under self-play — a direct descendant of Arthur Samuel’s 1959 checkers program4 and Gerald Tesauro’s TD-Gammon.5 Everything here is implemented in a single self-contained HTML file; this document explains exactly what that code does and why.

1Introduction & scope

Beetle Battle is a two-player game on an n×n grid. Players alternately place a beetle on an empty square or one they already own. Every square has a capacity equal to its number of orthogonal neighbours — two in a corner, three on an edge, four in the interior. The instant a square holds beetles equal to its capacity, it “explodes”: one beetle jumps to each neighbour, and any enemy beetles those neighbours hold are converted to the mover’s colour. Those neighbours may now be over capacity, so they explode too, and a single placement can set off a long chain reaction. A player wins when the opponent has no beetles left.1

That chain reaction is the whole problem. It makes the game thrilling to watch and very hard to evaluate, because the consequence of a move is not local — it can ripple across the entire board. This document covers, in order: why we learn an evaluation function rather than search for one (§2); how the game is framed as a sequential decision problem (§3); the representation we actually learn to value (§4–5); the learning rule itself (§6); how self-play, exploration, and the training loop fit together (§7–9); and how the trained agent plays, is measured, generalises, and is saved (§10–13). §14 is candid about what this simple method cannot do.

Design goals The agent must learn from zero domain knowledge, train fast enough to run live in a browser tab (thousands of games in seconds, no GPU), produce an evaluation function a person can read and interpret, and remain faithful to the original game’s rules and one-ply move-selection structure. These goals rule out heavyweight deep networks and favour a small, transparent, linear model.

2Why learning, not search

A natural first instinct for any board game is brute-force lookahead: try every move, every reply, every counter-reply, and pick the line that ends best. This is the minimax idea behind classical chess engines.7 It collapses quickly here. On a 5×5 board the opening player has 25 legal placements; the reply has ~24; and the branching factor stays high for the whole game because almost every square is always a legal move. Worse, a single move can trigger a cascade that rewrites a large fraction of the board, so positions do not simplify the way they do in chess endgames. Searching even a handful of plies ahead on an 11×11 board means examining an astronomical number of positions — the combinatorial explosion that Bellman named the “curse of dimensionality.”6 The original game’s own manual flags this explicitly as the reason a heuristic is required.1

The escape route, known since Shannon and Samuel, is to not search to the end. Instead, look only one move ahead, and replace the missing deep search with a learned function that estimates — from the shape of a position alone — how good it is. Samuel’s checkers program did exactly this in 1959: it adjusted the weights of a board-evaluation polynomial by playing against itself, and it improved.4 Our agent is a small, modern restatement of that idea. The art is entirely in (a) what features describe a position, and (b) how the weights on those features are learned.

3The game as a Markov decision process

To learn from experience we frame play as a Markov decision process (MDP), the standard formalism of reinforcement learning.2 At each step there is a state (the full board: how many beetles on each square and who owns them, plus whose turn it is), the mover chooses an action (a legal placement), and the environment responds with a new state — here, the board after the placement and any resulting cascade. The defining “Markov” property holds: the board contains everything needed to decide the next move; how the position was reached is irrelevant.

The reward structure is deliberately minimal and is what makes this a hard credit-assignment problem. The agent is told nothing about whether an individual move was clever. It receives a reward of +1 if it eventually wins, 0 if it loses, and nothing in between. The central difficulty — how to tell which of the forty moves in a winning game actually deserve credit — is solved in §6.

The game is two-player and zero-sum: one player’s win is the other’s loss. We handle this with a single value function always written from the mover’s point of view, and by having the two seats share one set of weights (§7). There is no chance element: transitions are deterministic, so the environment is an opponent rather than a dice cup.

4Afterstates: choosing the right thing to value

Before we can learn a value, we must decide what carries the value. There are three classic choices,2 and picking the right one is the single most important design decision in this system.

An afterstate (or “post-decision state”) is the board after the mover has placed a beetle and all cascades have resolved, but before the opponent moves. Because the rules are deterministic, the mover has complete control over which afterstate is produced by a given placement. This makes the agent’s job clean: enumerate the legal moves, simulate each one to the afterstate it produces, score every resulting board with the value function, and choose the best. We never need to model the opponent’s reply explicitly — that uncertainty is folded into the learned value of the afterstate itself. This is the representation Sutton & Barto recommend for exactly this class of game,2 and it mirrors how the original engine was already structured (copy the board, apply the move, score the result).1

5The value function

5.1Features in, win-probability out

The value function takes a board and returns a single number between 0 and 1, interpreted as the mover’s probability of eventually winning. It works in two stages. First a hand-designed feature extractor reduces the raw board to a short vector f(s) = (f0, f1, …, f9) of ten numbers, each measuring one interpretable property (material, territory, corner control, and so on — see §5.3). Then those numbers are combined linearly with learned weights w and passed through a squashing function.

This is a linear function approximator with a logistic output — equivalently, logistic regression whose targets are supplied by reinforcement learning instead of a labelled dataset. Using a linear model (rather than a neural network) is a deliberate trade: it cannot represent arbitrarily subtle interactions between features, but it trains in milliseconds, never diverges catastrophically, and every weight can be read off and understood.

5.2The logistic squashing function

The weighted sum z = w · f can be any real number, but a probability must lie in (0, 1). The sigmoid (logistic) function performs that mapping:9

σ(z) = 1 / (1 + e−z)maps any real number to the open interval (0, 1)

So the full value function is

v(s; w) = σ( ∑i wi fi(s) ) ≈ P( mover wins | board s )a linear combination of features, squashed into a probability

5.3The ten features

All features are computed from the mover’s perspective (“mine” vs “theirs”), and all are normalised so their magnitudes are roughly comparable and largely independent of board size — the property that lets one trained brain play on a board it never trained on (§12). A square is called loaded (the engine’s term is critical) when it holds exactly one beetle fewer than its capacity, i.e. a single further beetle makes it explode.1

f₂Territory(my squares − their squares) / n². Board control, independent of stacking.

6Temporal-difference learning

6.1Prediction by bootstrapping

We now have a value function but no way to set its weights. The reward only arrives at the end of the game (§3), so the obvious approach — wait for the final result and then nudge every position visited towards that result — is possible. It is called the Monte-Carlo method, and it works, but it is noisy: a single lucky or unlucky game shifts the estimate for every position in it.

Temporal-difference (TD) learning, introduced by Sutton in 1988,3 does something subtler and is the heart of this system. Instead of waiting for the final outcome, it updates each position’s value towards the value of the next position the agent reaches. Each estimate is pulled into agreement with the estimate that follows it — a process called bootstrapping, because the predictions lift themselves into accuracy by leaning on one another. Only the final move has a ground-truth target (the actual win or loss); that truth then propagates backwards, one link at a time, across many games. TD is the method behind both Samuel’s checkers player and TD-Gammon.4,5

6.2The TD(0) update rule

Let at be the afterstate the mover produced on its previous turn and at+1 the afterstate it produces on its current turn. The one-step temporal-difference, or TD(0), update is:

δ = v(at+1) − v(at),    w ← w + α · δ · ∇w v(at)δ is the TD error; α is the learning rate (step size)

The TD error δ measures surprise: how much the new estimate differs from the old one. If things turned out better than the previous afterstate predicted, δ is positive and we shift the weights to raise v(at) next time; if worse, we lower it. The learning rate α (default 0.08) controls how big each nudge is. The factor ∇w v is the gradient — the direction in weight-space that most increases the value — derived next.

6.3Gradient of the logistic value

Because v = σ(w · f) and the logistic function has the tidy derivative σ′(z) = σ(z)(1−σ(z)), the chain rule gives a gradient that is just the feature vector scaled by a single number:

∇w v = v · (1 − v) · fthe “confidence” factor v(1−v) is largest at v = 0.5

Substituting back, each weight is updated by

wi ← wi + α · &bigl[ target − v(at) &bigr] · v(at)(1 − v(at)) · fi(at)this is exactly the code in the implementation’s tdUpdate

The v(1−v) term is quietly important. It is near zero when the model is already confident (v close to 0 or 1) and maximal when the model is unsure (v near 0.5). Learning therefore concentrates on genuinely uncertain positions and barely disturbs settled ones — a built-in form of stability that comes for free from the logistic choice in §5.2.9

Implementation note In code, target is the value of the next afterstate, v(at+1), while the game is in progress, and is replaced by the true terminal value when the game ends (next section). The previous afterstate’s features f(at) are cached per player between their turns.

6.4Rewards & terminal targets

When a game ends, the bootstrap target is replaced by the real outcome — this is the only ground truth in the whole process:

  • the winner’s last afterstate is updated towards 1;
  • the loser’s last afterstate is updated towards 0;
  • if a game hits the move cap without resolving (a rare near-stalemate), both final afterstates are updated towards 0.5, treating it as a draw.

Because both seats are the same agent (§7), every game produces two learning trajectories — a winning one ending in 1 and a losing one ending in 0 — so each self-play game teaches the agent about both success and failure simultaneously.

7Self-play

The agent has no opponent to learn from, so it becomes its own. A single weight vector plays both seats: on red’s turn it chooses red’s move and evaluates positions from red’s perspective; on blue’s turn it does the same for blue. Because every feature is computed relative to whoever is moving (§5.3), the very same weights express “good for me” for both colours without modification.

Self-play is what lets the system bootstrap competence from nothing: as the weights improve, the quality of the opponent improves in lockstep, so the agent always faces a roughly equal adversary and is continually pushed to get better. This co-evolution is the same mechanism that, scaled up with deep networks and tree search, produced TD-Gammon5 and later AlphaGo Zero and AlphaZero.12,13 Its known risk is that a self-player can fixate on beating its own habits and develop blind spots an outside opponent would punish; the exploration of the next section is the main defence, and evaluation against an independent baseline (§11) is how we detect the problem.

8Exploration vs exploitation

If the agent always played the move its current weights rank highest, it would keep replaying the same games and never discover that a move it currently underrates is actually strong. This is the classic exploration–exploitation dilemma.2 The standard remedy is an ε-greedy policy: with probability 1−ε take the best-looking move (exploit), and with probability ε take a random legal move (explore).

We use a decaying schedule. Early in training the agent should experiment widely; later, once its judgement is worth trusting, it should mostly exploit so its value estimates converge on strong play. ε therefore falls linearly from 0.30 at the first game to 0.04 at the last, held constant within each individual game.

9The training loop

The pieces assemble into one compact loop. For each self-play game the agent alternates seats, and on every move it (1) chooses an afterstate ε-greedily, (2) applies the TD update to its previous afterstate using the chosen one as the bootstrap target, then (3) commits the move. At game end it applies the terminal targets of §6.4.

# one self-play game (afterstate TD(0))
state ← empty board;  prev[red] ← prev[blue] ← none
while game not over and moves < cap:
    p ← player to move
    # evaluate every legal move's resulting afterstate, pick eps-greedily
    choice ← choose_move(state, p, w, eps)     # value = sigma(w·f) , or 1 if it wins
    if prev[p] exists:
        td_update(w, prev[p].features, target=choice.value, alpha)
    state ← choice.afterstate;  prev[p] ← choice
    if choice wins:
        td_update(w, prev[winner].features, target=1, alpha)
        td_update(w, prev[loser].features,  target=0, alpha)
        break
# draw (hit move cap): nudge both last afterstates toward 0.5

# whole training run
for g in 1 .. G:
    eps ← linear_decay(0.30 → 0.04, g, G)
    play one self-play game
    if checkpoint(g): evaluate vs random, record win-rate

10Playing a move

Move selection during a real game against a human is the same routine used in training, with exploration switched off (ε = 0). The agent enumerates its legal moves, simulates each one — placement plus full cascade — to the afterstate it yields, scores every afterstate with the learned value function, and plays the highest. A move that wins immediately is assigned value 1 so it is always taken. Ties are broken at random, which keeps repeated games from being identical. This is a one-ply greedy search guided by a learned evaluation — structurally identical to the original engine’s move selection, but with discovered weights in place of hand-set ones.1

Why one ply is enough here Deeper search would help, but because the value function already estimates the eventual outcome of a position, one ply of real lookahead plus a good evaluation captures most of the benefit at a fraction of the cost — the same bargain Samuel and Tesauro struck.4,5 Extending the search depth is listed as a future option in §14.

11Evaluation & instrumentation

Self-play win-rates are meaningless as a progress measure — the agent always wins exactly half its games against itself. Strength is therefore measured against an independent, fixed baseline: a player that moves uniformly at random. At regular checkpoints during training, the current weights play a batch of games versus this random player (alternating who moves first, scoring a draw as ½), and the win-rate is recorded.

The second instrument is the weight vector itself, displayed live as a signed bar chart. Because the model is linear, every weight is directly interpretable as “how much this feature counts, and in which direction.” A typical trained brain on 5×5 looks like this:

12Generalisation across board sizes

Every feature is normalised by a board-size quantity — the number of squares n², the four corners, or the 4(n−2) edge squares (§5.3). As a result the feature vector for a given kind of position has a similar magnitude regardless of n, and a weight vector trained on one board carries over to another. Empirically, a brain trained only on 5×5 plays a 7×7 board against a random opponent at a similar high win-rate. It is strongest on the size it practised — some tactics are scale-specific — but it is never lost on an unfamiliar board. This is a small instance of the broader point that good feature design, not raw capacity, is what makes a linear model transfer.

13Persistence: saving a brain

A trained agent is nothing more than its ten weights plus a little bookkeeping, so it serialises to a tiny JSON object (under a kilobyte):

{
  "app": "beetle-battle-rl", "version": 1,
  "features": ["Baseline", "Beetle advantage", …],
  "weights": [0.152, 0.595, …],   # the entire learned strategy
  "trained": 3000,                  # games of experience
  "points": [ … ]                  # win-rate history for the chart
}

This can be exported to a file the user keeps and re-imported later, with the restored agent playing bit-for-bit identically (the JSON number format round-trips IEEE-754 doubles exactly). Where the host environment offers cross-session storage, a one-click quick-save/quick-load uses the same object. Carrying the features list and a version field alongside the weights lets a loader sanity-check that a file really is a Beetle Battle brain before trusting it.

14Limitations & extensions

This design intentionally sits at the simple end of the reinforcement-learning spectrum. Its limits, and the natural next steps, are:

  • Linear ceiling. A linear model cannot capture interactions between features (e.g. “a corner is only valuable if a chain backs it up”). Replacing the weighted sum with a small neural network — the TD-Gammon move5 — would lift this ceiling at the cost of training time and interpretability.
  • One-step credit assignment. TD(0) propagates outcome information one link per game. Eligibility traces — TD(λ)3 — would credit longer runs of moves at once and typically speed learning.
  • Shallow search. One-ply lookahead is cheap but tactically short-sighted. A few plies of minimax or a Monte-Carlo tree search over the same learned value — the AlphaZero recipe13 — would sharpen play considerably.
  • Hand-built features. The ten features are human-designed; a deep network learning directly from the raw board (as in DQN for Atari10 and AlphaGo for Go11) removes that bottleneck but discards the legibility that is a goal here.
  • Self-play blind spots. As noted in §7, an agent that only ever faces itself can develop exploitable habits; periodic evaluation against varied opponents, or a league of past versions, would harden it.

None of these are needed for the stated goal — a fast, transparent agent that learns to play Beetle Battle well from zero knowledge — but each is a clearly marked road onward.

§Glossary

AfterstateThe board immediately after a move and its cascade resolve, before the opponent replies. What the agent learns to value.
BootstrappingUpdating an estimate toward another estimate rather than toward observed ground truth.
ε-greedyA policy that exploits the best-known move with probability 1−ε and explores randomly with probability ε.
FeatureOne interpretable number summarising a property of the board (e.g. corner control).
Learning rate (α)Step size controlling how strongly each update moves the weights.
Loaded / critical squareA square holding one beetle fewer than its capacity — one placement from exploding.
MDPMarkov decision process: the state–action–reward formalism underlying reinforcement learning.
Sigmoid (logistic)The function σ(z)=1/(1+e−z) mapping any real number into (0,1).
TD error (δ)The difference between successive value estimates; the signal that drives each update.
Value functionA map from board to estimated probability that the mover eventually wins.
